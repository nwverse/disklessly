# Research follow-up: Luna (2026-10-20)

Scope: verification/extension of [`research.md`](research.md). I inspected the AppPorts and App Playpen repositories directly and checked Apple, Pake, and project documentation. “Verified” below means supported by linked primary/API/source material; behaviors called out as **Mac test required** are not claimed as established. No macOS machine was available for runtime experiments.

## 1. iCloud Drive / File Provider

### Dataless, download and eviction

- **Verified (API contract):** `FileManager.startDownloadingUbiquitousItem(at:)` requests materialization of an iCloud ubiquitous item; it is asynchronous and returning successfully does not mean bytes are downloaded. Poll resource values such as `ubiquitousItemDownloadingStatus` (`.notDownloaded`, `.downloading`, `.current`) and `ubiquitousItemIsDownloading` / percent downloaded where available. Apple describes status as the local copy's state, not a guaranteed progress stream. [Apple API](https://developer.apple.com/documentation/foundation/filemanager/startdownloadingubiquitousitem(at:)), [URLResourceKey](https://developer.apple.com/documentation/foundation/urlresourcekey/ubiquitousitemdownloadingstatuskey), [status values](https://developer.apple.com/documentation/foundation/urlresourcekey/ubiquitousitemdownloadingstatus).
- **Verified (API contract):** `evictUbiquitousItem(at:)` asks the system to remove the local copy of a ubiquitous item; it does not delete the cloud item. It can fail if the item is not eligible/available or is being used. [Apple API](https://developer.apple.com/documentation/foundation/filemanager/evictubiquitousitem(at:)). `NSMetadataQuery` with ubiquitous-item predicates can observe metadata and download status, but should be treated as event-driven hints and re-stat the item after updates. [Apple metadata query](https://developer.apple.com/documentation/foundation/nsmetadataquery).
- **brctl:** `brctl download <path>` requests download; `brctl evict <path>` requests local eviction; `brctl status` and `brctl log` are diagnostic interfaces, not a stable programmatic progress protocol. `brctl` is an Apple troubleshooting tool whose output/flags can change by OS release; don't parse localized text or make it the production contract. [Eclectic Light brctl guide](https://eclecticlight.co/2020/03/16/using-brctl-to-monitor-icloud-drive/), [brctl man page mirror](https://www.manpagez.com/man/1/brctl/). **Current macOS flag/output semantics need test on target releases**; use Foundation APIs in Swift as the primary implementation.
- **File Provider mechanics:** Sonoma's Drive has dataless placeholders with metadata local and content fetched on access, but it is misleading to state that *all* Sonoma+ iCloud operation reduces to a simple “copy/non-copy mode”. Optimize Mac Storage and provider policy affect retention, but user pinning and system policy can override assumptions. [Apple: manage iCloud files](https://support.apple.com/guide/mac-help/check-icloud-drive-file-folder-status-mac-mchlc994344b/mac), [Eclectic Light on Optimize Mac Storage](https://eclecticlight.co/2024/03/11/icloud-drive-in-sonoma-optimise-mac-storage-or-not/).
- **Non-sandboxed CLI:** likely can invoke FileManager APIs on the current user's iCloud Drive paths, but API availability is not proof that a particular process has provider permissions, correct ubiquity identity, or that eviction succeeds. **Needs test on Mac** with a non-sandboxed signed CLI, Optimize Storage on/off, Finder pin state, and in-use file. Apple APIs are documented for ubiquitous items; there is no promise that arbitrary command-line clients bypass File Provider policy.
- **Keep Downloaded / optimization:** Finder's Keep Downloaded is a user-level pin/retention policy (supported in current macOS versions; system may report download status), not an app-owned immutable lock. Do not evict a user-pinned image without explicit consent. Optimize Mac Storage off can retain local copies; it does not mean the app can assume every item is forever local. [Apple user guide](https://support.apple.com/guide/mac-help/check-icloud-drive-file-folder-status-mac-mchlc994344b/mac), [Eclectic Light Sequoia pinning](https://eclecticlight.co/2024/09/16/sequoia-introduces-pinning-to-icloud-drive/).
- **Large DMGs:** a DMG is a single ubiquitous file, so opening/reading it requires its bytes; no documented iCloud block-range-download contract exists for a normal app. Set an upload/download state machine and verify full local size + SHA-256 before attach. The `50 GB` statement in research.md is not a safely timeless universal rule: Apple's help page states current per-file limits/status (Ineligible), but limits may vary by service/OS and should be quoted with the date/source, not hardcoded as architectural guarantee. [Apple status guide](https://support.apple.com/guide/mac-help/check-icloud-drive-file-folder-status-mac-mchlc994344b/mac).
- **APFS clone:** `cp -c` requests a clone (copy-on-write) where supported; it is not a guaranteed independent physical copy. Whether a clone made from a cloud-backed file fully materializes and survives eviction of the source is not specified by `cp` semantics and depends on provider/APFS behavior. **Must test**: force source current, clone, verify/hash clone, evict original, reboot/offline, hash clone. Until proven, use an ordinary verified copy into cache and accept the disk-space cost. [cp(1) macOS](https://ss64.com/mac/cp.html), [APFS overview](https://support.apple.com/guide/disk-utility/file-system-formats-dsku19ed921c/mac).
- **Upload completion/conflicts:** “copy finished” is not “cloud upload complete”. Apple's ubiquitous metadata exposes upload status/progress keys (`ubiquitousItemIsUploading`, `ubiquitousItemUploadingError`, percent uploaded); wait for not-uploading and no error, then ideally confirm another device can retrieve/hash the item. [Apple URL resource keys](https://developer.apple.com/documentation/foundation/urlresourcekey). Concurrent edits can produce conflict versions; use immutable content-addressed DMG names and a per-device append-only manifest, and surface unresolved conflicts rather than auto-overwrite. File Provider conflict handling is not a transactional distributed catalog. [NSFileVersion](https://developer.apple.com/documentation/foundation/nsfileversion).

## 2. Stub bundle, Launch Services and forwarding

- A standard bundle needs `Foo.app/Contents/Info.plist`, `Contents/MacOS/<CFBundleExecutable>`, and optionally `Contents/Resources/` (icon, localized resources). A bundle whose executable is a shell script is fragile; Finder/Launch Services expects an executable and a shell script cannot implement Cocoa's `application(_:openFiles:)` Apple Event handling. **Use a tiny compiled Swift/AppKit launcher** (or a robust native helper) for document and URL forwarding. AppPorts has a concrete standalone Swift launcher with `NSApplicationDelegate.application(_:openFiles:)`, and reads the target path from Resources. [AppPorts source](https://github.com/wzh4869/AppPorts/blob/main/Tools/StubLauncher/StubLauncherSource.swift), [Apple bundle keys](https://developer.apple.com/documentation/bundleresources/information-property-list).
- **macOS 27 caveat:** source `research.md` says `CFBundleExecutable` “must” exist because of stricter bundle checks. Apple's standard bundle structure and app validation expect the executable, but the cited LibreSprite change is a project-specific report, not a general Apple policy document. Make it a required generated key regardless; **the claimed OS 27 enforcement details need verification against official release notes and a macOS 27 test**. [Apple bundle programming guide](https://developer.apple.com/library/archive/documentation/CoreFoundation/Conceptual/CFBundles/BundleTypes/BundleTypes.html), [LibreSprite issue/PR](https://github.com/LibreSprite/LibreSprite/pull/627).
- Register copied `CFBundleDocumentTypes` and `CFBundleURLTypes` on the stub only if the app's behavior is intentional. Launch Services associations are per declarations/registration and duplicate declarations for real app + portal can make “Open With”/default selection ambiguous. Forward file arguments as paths using `/usr/bin/open -a <real.app> --args ...` **is not document forwarding**: `--args` passes command-line flags to the executable, while a document must be opened as a document (e.g. `open -a <real.app> <file>` or `NSWorkspace.open(urls:withApplicationAt:configuration:)`). URL schemes likewise should be sent through Launch Services or handled by Apple Events; test URL forwarding, spaces, multiple files, and cold-start races. [open(1)](https://www.manpagez.com/man/1/open/), [NSWorkspace open URLs](https://developer.apple.com/documentation/appkit/nsworkspace/open(urls:withapplicationat:configuration:)).
- Prefer `NSWorkspace.openApplication(at:configuration:)` for launching the app and `open(urls:withApplicationAt:configuration:)` for documents; it returns launch results/errors and avoids shell quoting. [Apple NSWorkspace](https://developer.apple.com/documentation/appkit/nsworkspace).
- Copy the original icon resource (`CFBundleIconFile`/icns) into stub Resources, but the stub has its own bundle identifier and version/display metadata. Don't copy the target's identity wholesale. Keep a unique portal ID, register associations deliberately, and test `lsregister -u <portal>` only against the portal path; Launch Services database cleanup/rebuild tools are diagnostic and undocumented. `-nobrowse` suppresses Finder browsing/visibility of a mounted volume, not Launch Services registration of the actual mounted app.
- **Signing:** ad-hoc (`codesign -s -`) is adequate for local experiments but no stable Developer ID identity/notarization and can have Gatekeeper/permission consequences; signing the stub must not rewrite/re-sign the real app. Developer ID + hardened runtime/notarization is the distribution path, not a prerequisite for every private local tool. Changing `Info.plist` after signing invalidates the seal; write plist/resources first, then sign. [Apple code signing guide](https://developer.apple.com/documentation/security/code_signing_services), [notarization](https://developer.apple.com/documentation/security/notarizing_macos_software_before_distribution).
- **Quarantine/translocation:** quarantine is an extended attribute; App Translocation can affect downloaded quarantined apps opened through Launch Services. Do not blindly strip quarantine from user apps or assume a DMG/stub is quarantine-free. Preserve provenance and test Gatekeeper on the actual packaging workflow. [Apple DTS](https://developer.apple.com/forums/thread/724969), [Eclectic Light](https://eclecticlight.co/2024/05/14/lost-in-translocation/).

## 3. hdiutil lifecycle

- `hdiutil attach -readonly -nobrowse -noautoopen -mountpoint <dir> -plist <image>` is an appropriate baseline. Parse the plist, not human output; map mounted volume(s), device entry (`/dev/disk…`), and image path from returned entities and persist ownership to detach exactly the image mounted by this instance. [hdiutil man page](https://www.manpagez.com/man/1/hdiutil/).
- Re-attaching a mounted image may produce existing-device/volume behavior rather than a clean new mount. Deduplicate by canonical image path plus `hdiutil info -plist` device entry; do not infer ownership from mountpoint alone. **Needs macOS test** across symlinked paths, same image attached elsewhere, and parallel stub launches.
- Detach only after all dependent app processes have exited and filesystem handles drain. “Resource busy” is expected when open files/processes remain; retry with bounded delay and report it. `hdiutil detach -force` risks forcibly unmounting underneath an app and data loss (especially with shadow/writable images); never use it as normal cleanup. `-force` must be opt-in recovery only. [hdiutil man](https://www.manpagez.com/man/1/hdiutil/).
- Detect app lifetime through `NSWorkspace.didTerminateApplicationNotification` for GUI apps; capture the actual launched PID/bundle identity and account for app helpers/multiple processes. Alternatives are `kqueue` process vnode notifications or polling `NSRunningApplication`; none alone detects all helper/reattach cases. Do not use the CLI launcher's exit as the app lifetime signal. [NSWorkspace notification](https://developer.apple.com/documentation/appkit/nsworkspace/didterminateapplicationnotification), [NSRunningApplication](https://developer.apple.com/documentation/appkit/nsrunningapplication).
- Sleep/wake and FileVault: during sleep network downloads pause, mounts can remain or become unhealthy, and login/FileVault state can constrain user-session services. On wake, revalidate image mount and cache hashes before declaring ready; resume download rather than assuming byte progress. **Needs Mac testing** (sleep during download/run, fast user switching, logout, FileVault preboot is not a normal user process).
- **ULMO/ULFO:** ULMO is UDIF LZMA compressed read-only; ULFO is LZFSE compressed read-only. Compression ratio vs create/attach/decompression speed depends on app data, CPU and OS; no universal 50–70% size or speed guarantee. Benchmark representative bundles on Apple Silicon and Intel. `hdiutil verify` checks image integrity; separately SHA-256 the exact remote/cache payload. Shadow files create a writable overlay and change the immutability/space-accounting model; omit for MVP unless an app demonstrably needs writes. [hdiutil manual](https://www.manpagez.com/man/1/hdiutil/), [Eclectic Light format comparison](https://eclecticlight.co/2024/12/16/are-sparse-bundles-faster-than-disk-images/).
- GitHub `macos-latest` runners are real macOS, but hdiutil behavior/performance and available filesystem/permissions can vary with ephemeral runner images. **No evidence found for blanket hdiutil “flakiness”**; build an isolated integration test with retries only for known transient runner setup, preserve diagnostics, and don't weaken product correctness based on a CI anecdote. [GitHub-hosted runner images](https://github.com/actions/runner-images).

## 4. Pake for management UI

- Verified from Pake CLI docs/source: Pake wraps a URL, local HTML file, or static directory containing `index.html`; examples include `pake ./dist --name MyTool`. It produces Tauri apps, can build macOS universal via `pnpm run build:mac` (`universal-apple-darwin`), and has `--show-system-tray` option documented in CLI. `--install`, dimensions, icon, and config are documented. [Pake repository](https://github.com/tw93/Pake), [CLI guide](https://github.com/tw93/Pake/blob/main/docs/cli-usage.md), [package scripts](https://github.com/tw93/Pake/blob/main/package.json).
- Pake is not itself a native macOS menu-bar-extra framework. Its system-tray option is a Tauri system tray feature (menu/tray behavior varies by platform); this is distinct from designing a polished `NSStatusItem` native app. Window close/hide behavior and tray interactions should be tested on macOS. [Pake README](https://github.com/tw93/Pake/blob/main/README.md), [Tauri tray docs](https://v2.tauri.app/learn/system-tray/).
- Pake can package local web UI but the Rust/Tauri app still needs native permissions and a secure bridge. Recommended: Pake UI is a presentation client; Swift daemon/CLI owns iCloud, hdiutil, code-sign validation, and lifecycle. Define versioned JSON request/response events (launch, status, pin, evict, cancel), progress events, and explicit errors. Prefer a Unix domain socket with user-only permissions over unauthenticated `http://127.0.0.1`; if HTTP, bind loopback only, authenticate with per-user random token, validate Origin/CSRF, and never expose privileged arbitrary command execution. Tauri commands/plugin IPC can call a packaged native helper when permitted; a LaunchAgent should own long-running lifecycle and survive UI closure. [Tauri IPC](https://v2.tauri.app/concept/inter-process-communication/), [Tauri security](https://v2.tauri.app/security/).

## 5. Comparable projects: source inspection

### AppPorts (`wzh4869/AppPorts`)

- Cloned and inspected current `main`; GitHub reports Apache-2.0. [Repository](https://github.com/wzh4869/AppPorts), [LICENSE](https://github.com/wzh4869/AppPorts/blob/main/LICENSE), [StubLauncherSource.swift](https://github.com/wzh4869/AppPorts/blob/main/Tools/StubLauncher/StubLauncherSource.swift), [portal docs](https://docs-appports.shimoko.com/en/migration-strategy/portal).
- Concrete reusable ideas: generate a real minimal portal rather than a symlink; bundle a native Swift `NSApplicationDelegate` launcher; store target reference in a resource file; handle `openFiles` Apple Events; localize “disk unavailable” feedback; protect real app from self-updaters; keep data migration separate from app-bundle migration; preserve original signature and refuse risky re-signing; explicit repair/recovery and backup paths.
- Pitfalls: their inspected native launcher is an **external-volume path launcher**, not our remote fetch/verify/mount lifecycle; its example launches each document with `/usr/bin/open -a <app> <file>` and needs tests for multi-file order/URL events. A fixed path resource is insufficient for a content-addressed cache; use daemon IPC/portal ID. AppPorts documents legacy signature replacement and sandbox/container migration as problematic; don't copy older symlink/re-sign strategies. Its docs explicitly caution identity and permissions can break, and its recent model prefers APFS mount migration for eligible data rather than container symlinks. [AppPorts macOS 27 guide](https://docs-appports.shimoko.com/en/macos-27.html), [portal strategy](https://docs-appports.shimoko.com/en/migration-strategy/portal).
- **License:** Apache-2.0 permits use/modification subject to license, notices, and applicable attribution/patent terms; if copying source, retain required notices and review dependencies. Prefer reimplementing the small concept/pattern rather than importing code blindly.

### App Playpen (`univ-of-utah-marriott-library-apple/app-playpen`)

- Cloned and inspected README, `Crappy_App_Logic.py`, launcher/build scripts and LICENSE. Repository's own description says it generates a disk-image launcher and supports pre-script, post-script, close-script; it creates a read-write shadow overlay and starts the app from it. [Repository](https://github.com/univ-of-utah-marriott-library-apple/app-playpen), [README](https://github.com/univ-of-utah-marriott-library-apple/app-playpen/blob/master/README.md), [source](https://github.com/univ-of-utah-marriott-library-apple/app-playpen/blob/master/Crappy_App_Logic.py), [MIT license](https://github.com/univ-of-utah-marriott-library-apple/app-playpen/blob/master/LICENSE).
- Reusable concepts: lifecycle hooks align directly with our core requirement; gather bundle metadata to generate launcher; separate post-mount setup from pre-launch; wait for app quit before close script/detach; support exceptional app setup and writable shadow state.
- Pitfalls: old Python/py2app + nib workflow, 2020/macOS 10.13–10.15 tested; README says launcher uses shadow and scripts, but not a modern secure daemon or robust remote download integrity. Shadow writes can silently diverge from the canonical image and accumulate; do not use by default. Treat scripts as trusted packaged code, not arbitrary user-controlled shell fragments. Project is MIT, with attribution/license preservation for reused code.

## 6. Corrections to `docs/research.md`

1. **iCloud “Optimize off means all files resident and cannot evict” is overconfident.** Provider APIs, pinning, and user/system behavior are not a binary app-controlled policy. Keep it as a user setting that changes behavior; always inspect status and handle eviction failure.
2. **50 GB per-file limit** should not be embedded as a fixed, timeless fact. Cite current Apple support guidance/date and treat service eligibility/limits as mutable.
3. **`brctl status` as upload/download progress** is not a reliable production API. Use Foundation resource values/metadata and treat brctl as diagnostics; verify upload completion on target OS.
4. **`cp -c` as “zero-copy cache”** does not establish an independent local copy. It may be a shared APFS clone and cloud-provider clone/eviction semantics are undocumented. Do not evict original before a tested, verified cache copy.
5. **“Stub copies document declarations, then `open -a ... --args/文件` forwards” is wrong/ambiguous.** `--args` passes argv, not document events. A shell script cannot receive Launch Services `odoc` Apple Events. Need a compiled Cocoa launcher registering document/URL handlers, and forward via NSWorkspace or proper `open` document arguments.
6. **`lsregister -u` after each unmount is not guaranteed to solve duplicate registrations** and is not a supported per-run lifecycle mechanism. Unique portal bundle ID + controlled document/URL declarations are safer; test registration and cleanup.
7. **App Translocation claim** that three conditions are sufficient and our DMGs “won't carry quarantine” is too categorical. Quarantine and launch history/path affect behavior; inspect xattrs and test actual delivery path; don't strip quarantine casually.
8. **DMG ULMO ratio/speed estimates and “hdiutil verify” claims** need representative benchmarks and separate SHA-256. UDIF checksum doesn't replace backend manifest verification.
9. **AppPorts status/architecture description outdated:** current source has a native Swift StubLauncher replacing shell launchers, and current docs distinguish old symlink methods from new defaults. It should not be described simply as “AppPorts already abandoned Contents links” without version/date; the project still acknowledges historical/manual link paths.
10. **Pake is viable as a web UI shell, not proof of native menu bar extra capability.** Pake has Tauri system tray support, but that is not a full native `NSStatusItem` management app API; validate tray UX and define secured IPC.
11. **App Playpen is MIT, not unlicensed/unknown**, and its source explicitly implements pre/post/close scripts via a legacy Python app and shadow-mounted writable image. Cite license and avoid implying its approach is a direct read-only implementation.
12. **macOS 27 statements** (new executable/signing constraints) rely in the original on one project change. Keep as target compatibility risk, not general official requirement until verified against Apple documentation and real macOS 27.
13. **GitHub runner hdiutil flakiness**: no primary evidence identified. Build tests and collect runner version/logs rather than state this as known property.

## Key implications for the design

- Make Swift/FileManager the source of truth for iCloud status; poll and expose indeterminate progress, and never equate “request accepted” with complete download/upload.
- Use an ordinary verified local cache copy until APFS-clone survival after iCloud eviction is proven on supported macOS versions.
- Stub must be a small compiled AppKit launcher with real Apple Event/document/URL handlers and a stable portal ID; route launch to a daemon by portal ID, not a stale mount path.
- Keep app image read-only; do not use shadow unless app compatibility specifically requires it. Attach with plist output and track exact device/image ownership; normal detach is graceful, never force by default.
- Separate lifecycle (download → verify → attach → launch → detect actual termination → delayed detach → LRU update) from Pake UI. Use authenticated local IPC/Unix socket and typed commands, not an open localhost command endpoint.
- Maintain immutable content-addressed DMGs, per-device manifests, explicit conflict handling, user-visible pin respect, and separate upload-complete state.
- AppPorts is a strong reference for portal and recovery UX; App Playpen confirms lifecycle hooks and highlights the risks of writable shadow state. Respect Apache-2.0 and MIT licenses if source is reused.

## Open questions needing tests on a real Mac

- Does a non-sandboxed Swift CLI get reliable start-download, status polling, and eviction for iCloud Drive items across Optimize Storage on/off and Finder Keep Downloaded states?
- Does an APFS `cp -c` clone remain fully readable/hash-identical after source eviction, logout, reboot, and offline operation?
- What exact upload-status transition reliably indicates a complete DMG upload, and how are conflict versions surfaced on current macOS?
- Does a large DMG download expose useful percent progress via URLResourceValues/NSMetadataQuery? What are timeout/retry behaviors?
- Document and URL Apple Events: cold-start stub handling, multiple documents, URL schemes, Launch Services registration and unregistration, and duplicate real-app registrations.
- `hdiutil attach -plist` behavior for already-attached image, parallel launches, mountpoint collisions; detach retry and `Resource busy`; sleep/wake during download/run.
- ULMO vs ULFO creation size, CPU cost, attach/first-launch latency for representative large apps on Apple Silicon and Intel; hdiutil tests on GitHub macOS runners.
- Stub signing, quarantine, notarization, Gatekeeper and TCC behavior in the actual distribution/install workflow; macOS 27 bundle validation.
- Pake/Tauri tray UX, local static UI packaging, native helper invocation, secure IPC, and app termination when multiple helper processes remain.
